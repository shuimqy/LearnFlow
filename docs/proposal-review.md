# 修改建议的模型处理

提出修改建议 → 保存建议与修改原因 → 点击“交由模型处理” → 查看模型意见和执行结果。
正文可以先保留当前版本，仅在原因中描述问题；模型会结合原因决定是否生成修订。

## 处理过程

1. 检查用户、课程、知识点和建议的归属、状态及版本。
2. 记录本次处理标识，读取当前知识、建议和修改原因。
3. 通过后端来源服务读取关联课件的文本与页面图，交给 `qwen3.8-flash` 审查。
4. 校验模型的 JSON Schema、引用标识和处理意见，再次检查知识版本。
5. 将适用的修订与历史记录、检索文本块放在同一事务中保存，返回模型意见与实际执行结果。

这里直接复用后端服务，不需要部署 MCP。来源读取和修订保存是固定的服务能力，
没有让模型生成 SQL、直接操作数据库或执行任意代码，也没有实现通用的模型工具调用循环。
页面中的处理结果来自数据库事务的执行状态，不能由模型自行声明“已经保存”。

## 模型意见与写入结果

| 模型意见 | 行为 |
| --- | --- |
| 采纳建议 `approve` | 使用建议中的原始标题、摘要和正文 |
| 修正后采纳 `revise` | 使用模型返回的完整修订，保留未受影响内容 |
| 不采纳 `reject` | 知识不变，建议标记为已拒绝 |
| 需要补充依据 `needs_evidence` | 知识不变，保留建议，提示补充来源后重新提出 |

返回结果包含意见、理由、建议修改项、参考来源、未核验内容和模型名称。
实际结果独立记录为 `applied`、`unchanged`、`rejected`、`needs_evidence`、`stale` 或 `error`，
并明确是否写入及写入的知识版本。模型生成了修订但因版本冲突未写入时，会保留意见并标记 `stale`。
结果保存在建议的 `llm_review` 字段中，刷新页面后仍可查看。模型使用的输入、输出 Token 数量也会记录。

处理接口沿用 `POST /courses/{course_id}/knowledge/{knowledge_id}/proposals/{proposal_id}/accept`。
响应保留原来的知识字段，并增加 `processing` 对象。
页面提供“删除”操作，删除建议记录及其模型处理结果，不调用模型，也不撤销已保存的知识修订。
正在被模型处理的建议暂不允许删除。旧版 `reject` 接口保留兼容，页面不再提供手动拒绝按钮。

## 来源与边界

最多读取当前正文和建议关联的前 4 个不同来源页。PDF 图片与文本层同时提供；
每页文本最多 6000 字符，图片用于检查公式与排版。未提供的其它来源会在输入中明确标记。
文件已删除或无法读取时，只提供之前保存的引用并标明无法重新核验。
模型必须区分课件依据、通用知识推理和依据不足，不能引用未提供的来源标识。
正文、建议和引用都按待分析的数据处理，提示词要求忽略其中的命令。

模型调用期间不持有知识行锁。返回后重新检查处理标识、知识版本和状态，过期结果不覆盖新内容。
重复点击处理中建议会返回冲突；进程中断后，处理标识最多保留 5 分钟，之后可以重试。
模型调用失败不直接采纳原建议；写入失败时回滚知识、修订和检索块，并允许重试。

## 验证

新增迁移 `0004` 只增加建议处理状态与模型意见字段，保留原有建议和知识。
启动脚本自动执行，也可以手动迁移：

```powershell
uv run --all-packages alembic -c backend/alembic.ini upgrade head
```

用固定的定义纠错样例验证真实模型返回，不读取或写入用户知识：

```powershell
uv run --all-packages python -m app.cli.proposal_probe
```

本机已用 `qwen3.8-flash` 实测普通推理依据下的建议审查，返回采纳意见与完整正文，使用 519 个输入 Token、310 个输出 Token。
自动化测试覆盖模型修订写入、拒绝、证据不足、来源读取、伪造来源拒绝、并发版本冲突、重复处理、事务回滚和用户隔离。
浏览器测试使用独立测试库与固定模型响应，不产生真实模型费用。
